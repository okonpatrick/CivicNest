# Service interface non-functional requirements

## Decision record

- **Status:** Initial requirements; targets are provisional until measured
- **Decision date:** 2026-11-25
- **Scope:** Resident-facing CivicNest web interfaces and their shared
  components. These requirements set acceptance criteria for future
  implementation; they are not a claim that the current application conforms.

### How to use this document

Apply the constraints below to each new or materially changed service route.
The submitting team records test results and any exception with the change.
Owners are accountable roles, not individual contributors. A failed
measurement blocks release unless the named owner approves a documented,
time-limited exception with a remediation date; accessibility and security
failures that expose users or sensitive information are not waived.

### Accessibility and responsive design

Target WCAG 2.2 Level AA for service interfaces. Automated checks supplement,
but do not replace, keyboard and screen-reader testing.

| Constraint           | Owner                                                                      | Threshold / expected behavior                                                                                                                                                                                                              | Verification                                                                                                                    | Remediation if it fails                                                                                                                     |
| -------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Semantic structure   | Service UI team; Frontend Platform team for shared shell                   | Each route has one descriptive page-level `h1`, one `main`, meaningful headings in order, and appropriate native controls and landmarks. No interactive control is represented only by a clickable generic element.                        | Testing Library role queries; axe scan with zero serious/critical violations; inspect the accessibility tree and heading order. | Replace non-semantic markup with native elements or correctly named roles; repair heading/landmark structure and rerun checks before merge. |
| Keyboard operation   | Service UI team                                                            | Every action is usable with keyboard alone; tab order follows visual/reading order; no keyboard trap; Escape closes dismissible overlays where applicable; Enter/Space activate controls according to their native semantics.              | Manual keyboard-only route walkthrough; component interaction tests with `user-event`; verify overlays and forms.               | Fix focus order and keyboard handlers or use native controls; add regression tests for the failing interaction.                             |
| Visible focus        | Frontend Platform team for shared styles; service UI team for local styles | Every focused interactive element has a visible indicator at least 2 CSS px thick with at least 3:1 contrast against adjacent colors; it is not clipped or obscured by sticky content.                                                     | Keyboard walkthrough at default and high-contrast settings; inspect computed styles and contrast with browser devtools.         | Correct shared tokens or component styles, ensure overlays/scrolling do not obscure focus, and retest affected routes.                      |
| Labels and names     | Service UI team                                                            | Every form control has a persistent programmatic label; buttons and links have accessible names that describe their purpose. Placeholder text alone is not a label.                                                                        | Testing Library `getByLabelText`/role queries and axe; manually inspect icon-only controls with a screen reader.                | Add or correct visible labels and accessible names; add an accessible query assertion for each affected control.                            |
| Validation feedback  | Service UI team                                                            | Invalid fields are identified in text, associated with their error using `aria-describedby`, and expose invalid state. On failed submit, provide a summary or move focus to the first invalid field; preserve entered values when safe.    | Submit invalid and valid forms using keyboard; assert error text, association, focus, and invalid state in component tests.     | Correct error association and focus behavior, make instructions actionable, and add tests for the invalid-submit path.                      |
| Error identification | Service UI team                                                            | Errors identify the affected field or operation and explain how to correct or recover; color is never the only signal. Status changes are announced to assistive technology where needed.                                                  | Test error-state text and accessible associations; inspect with screen reader and grayscale/high-contrast view.                 | Add specific text, programmatic association, and an appropriate live announcement; verify the recovery path.                                |
| Responsive reflow    | Service UI team; Frontend Platform team for shared layout                  | At 320 CSS px viewport width and at 200% zoom, content and controls reflow without page-level horizontal scrolling or loss of information/functionality. Exceptions require genuine two-dimensional content and an accessible alternative. | Browser responsive mode at 320 CSS px; zoom to 200%; check representative routes and form workflows.                            | Remove fixed-width layouts, wrap or stack content, and provide an accessible alternative for any necessary two-dimensional content.         |

### Performance

The following are provisional starting budgets for a resident-facing,
mobile-first interface, not universal targets. Validate them against a
production build and representative devices/routes; record measured values and
revise the budgets only with evidence and owner approval.

| Constraint                             | Owner                                                           | Provisional threshold / expected behavior                                                                                                                                                                                                                                           | Verification                                                                                                                                                                                                | Remediation if it fails                                                                                                                                                                                                                   |
| -------------------------------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Initial production JavaScript transfer | Frontend Platform team; service owner for route-specific chunks | At most 200 KB total compressed (gzip) JavaScript required for the initial route. This is a baseline to validate, not a measured result.                                                                                                                                            | Run `pnpm build`; use Vite's per-asset gzip output and sum only JavaScript assets loaded for the initial route. Confirm in browser Network panel with cache disabled.                                       | Identify the largest initial chunks, remove unused code, split route-only features, or defer non-critical work; rerun the production build and record the result.                                                                         |
| Initial production CSS transfer        | Frontend Platform team                                          | At most 50 KB total compressed (gzip) CSS required for the initial route. This is a baseline to validate, not a measured result.                                                                                                                                                    | Run `pnpm build`; sum gzip sizes for CSS loaded on the initial route and confirm in browser Network panel.                                                                                                  | Remove unused rules, reduce duplicated styles, or load route-specific styles only where needed; rerun and record the result.                                                                                                              |
| User-perceived loading                 | Frontend Platform team; service owner for route content         | Provisional Largest Contentful Paint (LCP) target: no more than 2.5 seconds at the 75th percentile on mobile. Before field data exists, use a repeatable Lighthouse mobile profile and record three runs' median LCP as a lab baseline; do not claim a percentile from lab results. | Lighthouse against the production preview on representative routes using mobile emulation; after real-user measurement is available, evaluate field LCP at p75. Record tool, route, build, and environment. | Optimize the largest content element, initial assets, render-blocking CSS, and server response; rerun the same measurement. If the baseline remains infeasible, propose an evidence-backed revised target instead of silently waiving it. |

### Security and data handling

| Constraint                  | Owner                                                                  | Threshold / expected behavior                                                                                                                                                                                                                                                                      | Verification                                                                                                                                                         | Remediation if it fails                                                                                                                                                                          |
| --------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Untrusted content rendering | Service UI team; Frontend Platform team for shared rendering utilities | Treat service/API/user-provided strings as untrusted. Render as text using framework escaping. Do not use `dangerouslySetInnerHTML` or equivalent for untrusted content; any approved rich-text use requires a reviewed sanitizer and explicit allowlist.                                          | Review rendering paths and dependencies; add tests with markup-like input proving it is displayed as text; lint/review any raw HTML API use.                         | Remove unsafe HTML rendering or apply the approved sanitizer; add a regression test and security review before merge.                                                                            |
| Browser configuration       | Frontend Platform team; deployment owner for production settings       | Browser-visible configuration (including every `VITE_*` value) contains only public, non-sensitive values. No API secret, password, token, private credential, or protected data may be bundled into client assets.                                                                                | Review `.env.example` and configuration changes; inspect built assets for newly introduced secret-like values; confirm secret-bearing operations remain server-side. | Revoke and rotate exposed credentials immediately, remove them from client configuration/history as appropriate, move use to a protected server-side environment, and verify the rebuilt assets. |
| Client-side logs            | Service UI team; Frontend Platform team for shared logging             | Logs and browser telemetry contain no personal/resident information, request payloads, credentials, tokens, or other sensitive data. Log only sanitized error categories and non-sensitive operational context.                                                                                    | Review console/telemetry call sites; exercise representative error flows and inspect captured output using synthetic data.                                           | Remove or redact sensitive fields, restrict logging to safe error metadata, and add a test preventing sensitive payloads from entering the logging helper.                                       |
| Dependency updates          | Frontend Platform team / dependency maintainer                         | Review each dependency update for advisories, maintenance status, compatibility, and license; run `pnpm audit` and the relevant test/build gates. Triage known critical vulnerabilities within 7 days and high vulnerabilities within 30 days, or document a risk owner, mitigation, and due date. | Review the dependency-change PR and audit output; run `pnpm test`, `pnpm typecheck`, and `pnpm build` for runtime dependencies.                                      | Revert or replace unsafe updates, upgrade to a fixed compatible version, or apply a documented mitigation with a deadline; repeat audit and tests before release.                                |

### Reliability and recovery

| Constraint              | Owner                                                                         | Threshold / expected behavior                                                                                                                                                                                                                 | Verification                                                                                                                                | Remediation if it fails                                                                                                                |
| ----------------------- | ----------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| Loading state           | Service UI team                                                               | Asynchronous content exposes a perceivable loading status; repeated controls cannot submit duplicate operations unintentionally; loading ends in success, empty, or error and never spins indefinitely.                                       | Component tests for pending-to-result transitions; manually throttle the network and inspect status announcements.                          | Add explicit pending state, prevent duplicate actions, and guarantee completion/error transitions; test delayed and rejected requests. |
| Empty state             | Service UI team                                                               | A successful response with no results is distinct from loading or failure, explains that there are no results, and offers a useful next action where one exists.                                                                              | Test an empty successful response and verify the visible message and action.                                                                | Add a dedicated empty-state message and relevant recovery/navigation action; add a test for zero results.                              |
| Request failure         | Service UI team; API owner for server behavior                                | Failed requests show a plain-language, non-sensitive explanation and a retry or other safe next step where recovery is possible. Preserve user input when safe; never present a failure as an empty successful result.                        | Reject or time out the request in tests; assert error state, retry behavior, and preservation of safe input.                                | Handle failure explicitly, add safe retry/backoff as appropriate, and test recovery and non-recoverable cases.                         |
| Unexpected client error | Frontend Platform team for error boundary; service UI team for route fallback | A render/runtime failure is contained by a user-visible fallback; the page offers a safe reload or return action and does not expose stack traces, internal paths, or sensitive state. Other application routes remain usable where possible. | Force a component failure in an error-boundary test; verify fallback, recovery action, and absence of exception details in the rendered UI. | Add or repair an error boundary and fallback, sanitize diagnostics, and add a regression test for the failing route.                   |

### Initial measurement snapshot

On 2026-11-25, `pnpm build` completed with Vite and reported the current
initial assets as 70.06 KB gzip JavaScript and 0.49 KB gzip CSS. These values
are a single local production-build baseline, not a guarantee for future
service routes or devices. No LCP result is claimed; measure it using the
method above before assessing that budget.

### Verification and exceptions

Before requesting review for an affected service interface, record the
relevant automated test, build, accessibility, and performance results in the
change description. Use the repository quality gates (`pnpm check`) and the
focused browser/manual checks above; a passing build alone does not establish
accessibility or performance conformance.

If a provisional budget is exceeded, attach the repeatable measurement and
environment, identify the accountable owner, document the remediation plan,
and set a recheck date. Do not describe a provisional target as met until
measured evidence supports that claim.
